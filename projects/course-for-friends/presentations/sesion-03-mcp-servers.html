Punto 1

Qué es un MCP server

Punto 1

¿Qué es un MCP server?

Por defecto, Claude Code solo puede trabajar con archivos en tu computadora — no puede tocar nada fuera de esa carpeta. Un MCP (Model Context Protocol) server es lo que extiende esa capacidad hacia afuera: un puente entre Claude Code y un servicio externo (una API, una base de datos, un board de Miro, lo que sea).

Analogía: piénsalo como un app store, o como el puerto USB-C universal — te conectas una vez al "puerto" y de ahí en adelante el agente sabe qué hacer con lo que sea que conectaste.

Punto 1

Mecánica, en 2 pasos

  1. Instalas el servidor MCP una vez y le das tu API key o credenciales — vía un archivo .env, nunca pegada directo en el chat
  2. A partir de ahí, Claude Code puede usar ese servicio cuando lo necesite — el agente lee las tools que expone el servidor MCP y decide sola cuál invocar según lo que le pediste

Punto 2

En miro-bpmn, en concreto

  • El MCP de Miro — tools como layout_create, layout_read, layout_update, board_create: las que de verdad dibujan figuras en un board real y visible
  • El SKILL.md de miro-bpmn — 6 pasos: localizar el discovery-output.md, analizar fases/tareas/gateways, pedir el board, construir el DSL, crear en Miro, validar con el usuario. Puro proceso, ni una figura se dibuja desde aquí

Punto 2

El momento "ahá"

Cuando alguien dice "dibuja el BPMN de [cliente] en Miro", Claude Code carga la skill miro-bpmn porque su description encaja con la petición — la skill es el cerebro que decide qué dibujar y en qué orden. Pero la skill por sí sola no puede tocar Miro: en el Paso 5 (Crear en Miro), le pasa el trabajo al MCP de Miro, que es quien realmente ejecuta layout_create y hace aparecer las figuras en el board.

Skill = cómo. MCP = manos.

Punto 2

¿Cuándo usar cuál?

La regla simple:

¿Necesitas que el agente toque algo fuera de sus archivos locales (un board, un email, una base de datos)? MCP. ¿Te encuentras repitiéndole lo mismo una y otra vez sobre cómo hacer algo? Skill.

Setup general

Cómo se conecta cualquier MCP server

Punto 3

Mismos 4 pasos, sin importar el servicio

  1. Crear un .env en el proyecto para guardar la API key
  2. Pedirle a Claude Code que instale/conecte el servidor MCP — cada servicio publica su propio comando de instalación
  3. Pegar la API key en el .env y guardar — nunca se pega directo en el chat
  4. Recargar la ventana (Cmd/Ctrl+Shift+P → "Developer: Reload Window")

Punto 4

No hace falta dominarlas todas

El MCP de Miro expone más de 30 tools — bastante más que un MCP típico como Firecrawl, que solo expone alrededor de 5.

miro-bpmn no usa las 30+ — solo necesita 4-5 del grupo de layout, más board_create cuando hace falta un board nuevo. Una skill bien enfocada no tiene que dominar todo lo que el MCP ofrece, solo la porción que su tarea específica necesita.

Punto 5

El patrón cheat sheet

Punto 5

¿Qué es un cheat sheet?

Cuando un MCP expone varias tools (como Miro con sus 30+), ayuda pedirle a Claude que genere un cheat sheet en markdown dentro del proyecto: qué tools hay disponibles y cuándo usar cada una, con el detalle técnico necesario. Le da a Claude Code una referencia rápida para acertar a la primera en vez de ir descubriendo a prueba y error.

Ejemplo real: miro-bpmn/reference.md — no es teoría, es el archivo que ya existe en este repo.

Punto 5

Qué contiene

  • Qué tool usar y cuál NO — layout_create sí, diagram_create no (ese solo sirve para flowchart/uml/erd genéricos, sin vocabulario para BPMN)
  • Constantes de layout exactas — distancias entre nodos, alturas de fila, tamaños de figura, para que cada diagrama salga con la misma proporción
  • Reglas aprendidas en producción — errores reales que ya pasaron y cómo evitarlos

Punto 5

Por qué se mantiene separado

El SKILL.md de miro-bpmn se queda corto y legible (los 6 pasos del proceso) y solo apunta al reference.md para el detalle técnico pesado.

Mismo criterio de "contexto mínimo necesario" que ya viste con el CLAUDE.md en la Sesión 1 — no todo tiene que vivir en el mismo archivo.

Punto 6

Self-healing en acción

La regla real de miro-bpmn

Punto 6

La situación

layout_create recibe el diagrama completo en una sola llamada — shapes, texto, conectores, todo junto. Si un solo parámetro está mal (ej. una figura con size < 10), el MCP rechaza todo el lote con un error HTTP 400 — no dice cuál de los 20-30 elementos fue el culpable.

Punto 6

La regla: bisectar

En vez de reintentar a ciegas o rendirse, bisectar — partir el lote a la mitad, reenviar cada mitad por separado para ver cuál falla, y repetir sobre la mitad culpable hasta aislar el elemento exacto.

La skill incluso anota de antemano dónde suele estar el problema: casi siempre es un size chico en un gateway.

Punto 7

Hands-on de cierre

Punto 7

MCP + mini skill, mismo patrón que miro-bpmn

Sobre el mismo proyecto de las Sesiones 1 y 2

  1. Identificar el servicio externo que te serviría tocar de verdad (Gmail, Airtable, Google Calendar, tu CRM)
  2. Conectarlo como MCP siguiendo los 4 pasos del Punto 3
  3. Explorar sus tools — pedirle a Claude Code que liste qué puede hacer ese MCP
  4. Construir una mini skill que lo use — framework de 6 pasos de la Sesión 2
  5. Probarla en vivo — tiene que producir un resultado real y visible, no solo texto
  6. Si algo falla — diagnosticar antes de rendirse, anotar la solución en el SKILL.md
